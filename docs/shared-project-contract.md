# Shared project v1

GET `/api/projects/{projectId}/shared?view=visitor` locally; `/xr-api/projects/{projectId}/shared?view=visitor` hosted. This is an additive read-only projection. Existing storage, authoring routes and publication semantics stay unchanged. The frontend and API require separate deployment; the current automated workflow deploys frontend only.

Envelope: `schemaVersion:1`, `contract:"nourishland.shared-project"`, `revision:"sha256:<64 lowercase hex>"`, `project`, `sites`, `areas`, `records`. Revision hashes canonical sorted object keys over the complete public payload, excluding the revision itself; it contains no generation timestamp. It is a change identifier, not a signature or numeric sequence. A repeated unchanged read has the same revision. Content, relationships and publication changes alter the revision.

Project: `{id,name,description}`. Sites add `projectId`; areas add `projectId,siteId`. Records: `{id,recordId,projectId,siteId,areaId,markerId,title,kind,knowledgeId,description,scientificName,profile}`. Record `id` is the JSON string tuple `[projectId,siteId,areaId,recordId]`. `recordId` is the original specimen instance ID for registry specimens, or directory marker ID for legacy marker-only records. `knowledgeId` retains species ID where present; multiple specimens can share it without sharing record identity. Empty marker/knowledge references remain empty. Profiles are the existing visitor-filtered legacy objects, deliberately retained rather than redefined as a new knowledge schema.

Only explicitly public ancestors and records enter the response. Hidden/private project requests return 404. Hidden sites/areas/markers/species/instances are excluded. The response allowlists project/record presentation fields and excludes Creator field_work. Profile projection uses the existing `publicPlantProfile` filtering for published/reviewed PIM nodes. This is the existing publication boundary, not new project-scoped authentication or native write authorisation.

`app/services/sharedProjectContract.js` validates the envelope, revision syntax, types, canonical tuple identity, duplicate IDs and project/site/area relationships. It is reused at the API output and Field/Desktop input boundaries. Unity must maintain equivalent native validation; it does not execute JavaScript. Unknown future schema versions fail rather than rendering guessed data. Missing/malformed content must not be represented as successful empty state.

Field/Desktop use the endpoint for project, area and profile opens/refreshes. They retain no stale snapshot when a refresh fails or publication is revoked. Global project discovery still uses the existing public project-list route. Offline personal journal/checklist behavior remains separate; this is not a downloaded project pack. Native integration is owned by Start Unity project port and must distinguish local adapter/editor checks from live backend availability and Quest validation.

Acceptance: one synthetic project, two specimens of one species, one legacy Totem; hidden ancestors/content excluded; profile PIM drafts excluded; no writes/migration during shared reads; repeated unchanged revision stable; an existing authenticated/local editor update changes the returned profile/revision without changing IDs. Fixture: `artifacts/platform-foundation/shared-project-example.json`. Native adapter tests should use that fixture then the same deployed API after a backend release.
